# Защита DNS — рабочая реализация

## Поведение

Защита действует, когда AutoTurn требует VPN. Дома в Auto/Home и после
выключения восстанавливается DNS текущей сети. Пользовательские настройки
сетевых служб и роутера не перезаписываются.

В «По правилам» работающий VPN используется для всех запросов встроенного
DNS. При сбое VPN DNS доменов, назначенных в VPN, получает временную ошибку;
обычные домены разрешаются через DoH напрямую. Выбранные домены и IP-сети
блокируются в routing core, пока новый VPN не проверен. Core продолжает
обслуживать прямые направления между попытками и профилями. Его пересоздание
может кратковременно прервать существующие прямые соединения. При недоступном
сервере и ещё работающем процессе VPN резерв включается после обнаружения
сбоя проверкой связи; до этого DNS может ждать таймаутов. Это не гарантия
непрерывного интернета без пауз.

В полном режиме прямого DNS-резерва для сайтов нет. При отказе туннеля
внешний трафик не выпускается напрямую. Проверка VPN использует выбранный
DNS через проверяемый utun, до открытия доступа защищённым доменам.

## DNS-провайдеры

Настройки → Защита DNS → Настроить DNS: основной и до двух резервных.
По умолчанию Cloudflare → Quad9. Доступны Google, DNS из VPN-профиля и свой
DoH. Quad9 9.9.9.9 фильтрует известные вредоносные домены. Порядок задаёт
последовательность попыток, без параллельной отправки всем провайдерам.

Хотя бы один DoH обязателен для первоначального подключения и прямого резерва.
«DNS из профиля» используется только через VPN; при прямом резерве пропускается.
Свой DoH требует HTTPS URL и известный IPv4, порт 443; TLS проверяется по
имени в URL. Обход проверки сертификатов не поддерживается.

В прямом резерве DNS-провайдер видит реальный IP клиента. Провайдер интернета
видит соединение к DoH, но содержимое запросов зашифровано. Для полного
сокрытия исходящего трафика нужен полный туннель.

## Реализация

- Root helper обслуживает только 127.0.0.1:53, UDP и TCP. Если порт занят,
  подключение завершается ошибкой при включённой защите PF.
- В полном режиме системный supplemental resolver направлен на loopback.
  В режиме правил synthetic DNS TUN пересылает реальные запросы туда же.
- DoH использует системный curl с `-q`, явным `--resolve`, `--interface if!…`,
  выключенными proxy, без редиректов, с проверкой TLS и ограничениями времени
  и размера ответа. Имя самого DoH не запрашивается у роутера.
- Адрес VPN Endpoint по имени запрашивается через DoH к известному IP.
  До туннеля в PF разрешён root HTTPS к выбранным адресам, без UDP/TCP 53.
- PF блокирует физический выход DNS 53/853 перед общим разрешением root
  для routing core; loopback и разрешённый VPN utun обрабатываются раньше.
- После смены профиля/сети старые DNS-ответы отклоняются по поколению.
  Кэш настоящих ответов routing core отключён. Fake-IP сохраняют имена,
  а не старый внешний маршрут; для offline-core VPN-правила становятся reject.
- Новый UI проверяет DNS-возможности helper и требует обновить старую службу.
  Профили и старые настройки мигрируют с защищёнными DNS по умолчанию.

## Границы

Это не гарантия отсутствия блокировок аккаунтов и не анонимизация браузера.
Встроенный DoH отдельных приложений — обычный HTTPS: при разрешённом прямом
интернете его невозможно универсально распознать. ECH и старые кэши могут
скрывать имя назначения; доменные правила не гарантируют классификацию всех
таких потоков. Для строгого покрытия используйте «Всё через VPN».

Если правило содержит только IP-сети, имя может быть разрешено прямым DoH
до того, как станет известно, что IP относится к VPN. Для важных сервисов
нужны доменные правила. Неизвестный заранее CNAME также может обнаружиться
лишь после запроса: защищённый ответ не возвращается через прямой резерв,
но уже сделанный запрос исходного обычного имени отменить невозможно.

Корпоративные локальные имена и captive portal могут требовать отключения
VPN пользователем; автоматического обращения к локальному DNS нет. IPv6-only
uplink и IPv6 Endpoint остаются неподдерживаемыми. DNS из профиля сейчас
опрашивается через IPv4; IPv6-only DNS профиля требует публичного DoH в резерве.

## Проверка без смены системной сети

```
AT_TEST_ROUTING_CORE="$PWD/third_party/routing-core/sing-box" bash scripts/test.sh
python3 scripts/test-routing-dns.py
AT_REUSE_ENGINE=1 AT_DIST="$PWD/dist/dns-preview" bash scripts/build.sh
bash scripts/smoke.sh "$PWD/dist/dns-preview/AutoTurn.app"
dist/dns-preview/AutoTurn.app/Contents/Library/LaunchServices/AutoTurnHelper --secure-dns-self-check
```

Последняя команда делает реальные HTTPS-запросы к трём публичным DNS,
не меняя DNS, маршруты, PF, Wi-Fi, Keychain или установленную службу.

Для проверки реальных утечек нужна установка новой службы и захват пакетов
на физических интерфейсах: обычный Wi-Fi без VPN на роутере, оба режима,
отказ DNS, обрыв VPN, переключение двух профилей, сон, смена сети и Off/Home.
Проверять обычный сайт и защищённый сервис, а не только оценку сайта Net.Coffee.
Состояние live-проверок фиксируется отдельно; loopback-тесты их не заменяют.

## Изменения после живых проверок

Встроенный DNS кэширует успешные ответы до 60 секунд, с учётом их DNS TTL.
Это убирает повторные обращения к DoH при открытии соединений с одним сайтом.
TTL в ответах уменьшается с возрастом записи. При смене сети, профиля, правил
или пути VPN/прямой резерв кэш очищается; защищённые ответы не переносятся
в прямой резерв. Отрицательные ответы и ошибки не кэшируются.

`AutoTurn --dns-live-check-stored` запускает ограниченную живую матрицу
с сохранённым профилем: правила, два временных профиля, недоступный VPN,
резервный DNS и полный туннель. Настройки меняются только в памяти helper;
Keychain и сохранённые маршруты не записываются. В конце восстанавливается
исходная конфигурация. Отдельный watchdog возвращает управление при зависании.
